# Отчёт: клиент-серверное приложение Taskboard

## Доменная область

Taskboard — небольшой список задач. Пользователь записывает, что нужно сделать, добавляет описание и меняет статус по мере выполнения. Через веб-интерфейс доступны создание, просмотр, редактирование и удаление. Все пользователи работают с одним списком; учётных записей нет.

## Стек и устройство

Бэкенд: **Kotlin 1.9.25, JDK 21, Spring Boot 3.5.16**, встроенный Tomcat. Фронтенд: **HTML, CSS, JavaScript**, без сборщика и дополнительных библиотек. Взаимодействие — **HTTP/1.1 REST, JSON**. Данные хранятся в **PostgreSQL 17.11**; доступ — JDBC с пулом HikariCP, схема управляется Flyway. Сборка — Maven с Kotlin-плагином, запуск окружения — Docker Compose. Исходники бэкенда и все тесты написаны на Kotlin.

Путь запроса: браузер → `TaskController` → `TaskService` → `TaskRepository` → `JdbcTaskRepository` → PostgreSQL. Контроллер принимает `TaskRequest` и преобразует его в `TaskDraft`, который проверяет содержимое задачи. Сервис выполняет операцию через интерфейс хранения. JDBC-реализация выполняет SQL, результат возвращается в JSON, после чего JavaScript обновляет страницу. Статика входит в JAR приложения.

Код разделён на пакеты `controller`, `dto`, `service`, `repository`, `model`, `exception`, `config` и `filter`. Модель и сервис не зависят от Spring, HTTP и JDBC. Сервис обращается только к интерфейсу `TaskRepository`, а SQL находится в его реализации `JdbcTaskRepository`. Контроллеры преобразуют запросы и ответы, `config` связывает части приложения через конструкторы. Это сохраняет разделение ответственности и независимость основной логики при привычной структуре папок.

## Основная сущность

В предметной области одна сущность — **задача** (`Task`, таблица `tasks`).

| Поле | Содержание |
|---|---|
| `id` | Числовой идентификатор, генерируется PostgreSQL |
| `title` | Непустое название до 160 символов |
| `description` | Описание до 4000 символов, может быть пустым |
| `status` | `TODO` — нужно сделать, `IN_PROGRESS` — в работе, `DONE` — готово |
| `created_at`, `updated_at` | Время создания и изменения; в БД `TIMESTAMPTZ`, в API UTC |

CRUD реализован маршрутами `POST /api/tasks`, `GET /api/tasks` и `GET /api/tasks/{id}`, `PUT /api/tasks/{id}`, `DELETE /api/tasks/{id}`. API проверяет форму JSON и типы, доменная модель — название и длину текста. Схема PostgreSQL тоже содержит ограничения. SQL-запросы параметризованы; изменение одной задачи выполняется одним атомарным запросом.

## Соответствие 12 факторам

Сопоставление выполнено по [The Twelve-Factor App](https://12factor.net/ru/). Часть факторов описывает порядок эксплуатации, поэтому рядом с устройством приложения указан способ его запуска и сопровождения.

| Фактор | Как соблюдается |
|---|---|
| **1. Кодовая база** | Фронтенд, бэкенд, миграции и описание окружения находятся в одном Git-репозитории. Для разных окружений используется одна версия исходников, меняется конфигурация. Архив для сдачи содержит исходники этой кодовой базы без служебной папки `.git`. |
| **2. Зависимости** | Библиотеки и Kotlin-плагин перечислены в `pom.xml`, версии определяет зафиксированный parent Spring Boot 3.5.16, включая Kotlin 1.9.25. Maven собирает исполняемый JAR с библиотеками. Dockerfile задаёт Maven и JDK/JRE 21; Compose — PostgreSQL. Глобально установленный Kotlin и JavaScript-пакеты не нужны. |
| **3. Конфигурация** | Адрес и доступ к БД, порт, уровень логирования и размеры пулов задаются переменными окружения. `application.properties` читает их через `${…}`. Для быстрого локального запуска `compose.yaml` задаёт учебные значения по умолчанию, включая явно демонстрационный пароль; приложение получает их через окружение. Собственные значения можно задать в `.env` или окружении без изменения Kotlin-кода и образа. Реальный `.env` исключён из Git и Docker-контекста, пример находится в `.env.example`. |
| **4. Сторонние службы** | PostgreSQL — подключаемый ресурс. Приложение знает только JDBC URL и данные доступа. Для перехода на другую PostgreSQL меняются `DB_URL`, `DB_USER`, `DB_PASSWORD`; код и JAR остаются теми же. Локальная БД из Compose — один из вариантов подключения. |
| **5. Сборка, релиз, выполнение** | `docker compose build app` собирает образ. Релиз задаётся версией образа (`APP_VERSION`) и конфигурацией, затем процесс `migrate` применяет миграции. `app` запускается только после его успешного завершения. В работающем контейнере исходники не компилируются и не редактируются. Новому релизу назначается новый тег; старые теги сохраняются. |
| **6. Процессы** | JVM-процесс не хранит задачи, пользовательские сессии или файлы состояния. Долговечные данные находятся в PostgreSQL, пул JDBC — только временный ресурс. Контейнер приложения работает с файловой системой только для чтения и временной `/tmp`; его можно заменить без потери задач. |
| **7. Привязка портов** | Исполняемый JAR сам запускает Tomcat и слушает HTTP-порт из `PORT`. Отдельный сервер приложений не нужен. Тот же HTTP-сервис отдаёт API и фронтенд; Compose публикует выбранный локальный порт. |
| **8. Параллелизм** | Пропускная способность увеличивается запуском дополнительных экземпляров `app`. Они используют общую PostgreSQL; привязки клиента к одному экземпляру нет. В том же `compose.yaml` можно задать `APP_PORT=0` через окружение и запустить `docker compose up -d --wait --scale app=2`: Docker назначит каждой реплике свободный порт. Заголовок `X-Instance-Id` различает ответы. Балансировщик добавляется отдельно. |
| **9. Утилизируемость** | Старт сервера не включает сборку или миграции. На `SIGTERM` Spring завершает текущие запросы с ожиданием до 20 секунд; Compose даёт процессу 30 секунд. При прерывании SQL-запроса PostgreSQL обеспечивает атомарность изменения. `/health/live` проверяет процесс, `/health/ready` — доступность таблицы задач. |
| **10. Паритет окружений** | Разработка и запуск в Compose используют один Dockerfile, одну PostgreSQL 17.11 и одни миграции. Интеграционные тесты тоже запускают PostgreSQL 17.11 через Testcontainers, без замены на H2. При прямом запуске из IDE используются тот же код, JDK 21, параметры подключения и PostgreSQL. |
| **11. Журналирование** | Приложение пишет события в stdout/stderr. `RequestLogFilter` фиксирует метод, путь, HTTP-код, длительность и экземпляр; содержимое задач и пароль в эти записи не попадают. Чтение и хранение логов — задача среды запуска, например `docker compose logs -f app`. Приложение не управляет файлами логов. |
| **12. Задачи администрирования** | Миграции выполняет отдельный короткоживущий процесс из того же образа: `docker compose run --rm migrate`. Он получает ту же конфигурацию БД, применяет SQL из JAR и завершается. HTTP-сервер в этом режиме не поднимается; повторный запуск уже применённой миграции не удаляет данные. |

## Проверка и ограничения

Команда `mvn verify` выполняет четыре модульных теста доменных правил и восемь интеграционных тестов на настоящей PostgreSQL. Интеграционные сценарии: полный CRUD по HTTP, невалидные запросы, отсутствующие идентификаторы, специальные символы, параллельное создание задач, повторная миграция, фронтенд и health endpoints. При недоступной таблице тест проверяет ответы `503` у readiness и API, работающий liveness и восстановление readiness после возврата таблицы. Быстрый запуск и ручная проверка описаны в `README.md`.

Для текущей Kotlin-версии выполнен `mvn clean verify`: все 12 тестов прошли без ошибок и пропусков. Собран Docker-образ `taskboard:1.1.0`, выполнен запуск через Compose; процесс миграций завершился с кодом 0, readiness вернул `UP`. После замены контейнера приложения все три существовавшие задачи сохранились без изменений. Автоматический прогон действий в браузере не выполнялся; проверены выдача статики и синтаксис JavaScript.

После упрощения запуска отдельно проверено новое окружение без `.env`: один `compose.yaml` собрал образ, запустил PostgreSQL, миграции и сервер. Выполнен полный CRUD по HTTP. Через тот же файл запущены две реплики с автоматически назначенными портами: задача, созданная через первую, прочитана и удалена через вторую.

Приложение намеренно небольшое: без авторизации, пагинации, фоновых очередей и автоматического разрешения конфликтов редактирования. При одновременном изменении одной задачи сохраняется последнее обновление. Это ограничения функциональности, а не препятствия для 12 факторов. Для промышленного размещения дополнительно понадобятся контроль доступа, резервное копирование и настройка среды эксплуатации. Реального production-окружения в рамках работы нет, поэтому регламент неизменяемых релизов и паритет с ним описаны как правила развёртывания.
